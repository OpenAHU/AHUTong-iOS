# iOS 原生支付协议兼容与安全边界

## 实现基线

PAY-01、PAY-02、PAY-03、PAY-05 的生产实现以 Android commit `2c33b0b` 为唯一协议参考。iOS 在 `YCardProductionPaymentGateway` 内执行与 Android 相同的客户端协议签名、安全键盘映射和订单提交，不再依赖 `SafetyBlockedPaymentGateway`，也不再提供学校官方页面兜底。

为保持现有生产协议兼容，App 包含 Android 已使用的客户端协议签名常量。常量只允许存在于生产支付兼容层的私有类型中；本文件、迁移路线图、日志、错误消息和验收记录都不得输出其值。它们不是用户的校园卡密码、Token、Cookie 或系统凭据。

`--demo-session` 仍只启用确定性内存订单，用于单元测试和 Android ↔ iOS UI 对照。Demo 不接触真实账号、真实密码或真实资金。

## 四条生产链路

- PAY-01 校园卡银行卡充值：查询卡账户，按 Android 的建单字段和签名规则创建订单，解析 `orderid`，再执行银行卡最终提交并刷新校园卡余额。支付宝小程序继续使用固定白名单跳转，且不向剪贴板写入身份或支付信息。
- PAY-02 浴室缴费：支持 `feeitemid` 409 和 430；先用 `paystep=0` 创建订单，随后用该业务的安全键盘规则映射六位密码，再以 `paystep=2` 提交并刷新所选浴室账户余额。
- PAY-03 电控缴费：创建已签名订单后，每个订单单独获取动态安全键盘材料，完成映射和已签名最终提交；成功后重新查询当前房间余额。
- PAY-05 网费充值：依次完成入口预热、账户查询和已签名建单；每个订单单独获取动态安全键盘材料，完成映射和已签名最终提交；成功后刷新网费账户。

PAY-02、PAY-03、PAY-05 的 `third_party` 不直接透传任意服务端对象，而是分别按 Android `2c33b0b` 的数据模型、字段顺序、空值规则和 Gson 字符串转义重新生成。所有校园卡 POST 表单统一采用与该 Android 版本 OkHttp `FormBody` 相同的 UTF-8 编码语义；URL query 与表单编码保持为两个独立实现，避免特殊字符在服务端解码后改变签名输入。

签名实现保持 Android `buildSignedFormBody` 的字段排序、空值处理、元数据和摘要大小写语义。测试以固定向量验证兼容性，但测试输出不得打印签名材料、完整表单、安全键盘映射或映射后的密码。

## 订单状态与重复提交保护

客户端在任何建单请求前先保存功能类型和 `creating` 阶段。拿到有效 `orderid` 后、获取安全键盘材料或执行最终提交前，立即保存 `orderid`、功能类型、支付方式和 `orderCreated` 阶段。

状态只允许按以下方向推进：

1. `creating`：建单请求尚未得到确定结果。
2. `creationUnknown`：建单结果未知；禁止自动再次建单，只能人工核验。
3. `orderCreated`：订单号已经安全保存；允许用户继续同一订单的确认流程。
4. `finalSubmissionStarted`：最终请求可能已经到达学校系统；禁止重放最终提交。
5. `resultUnknown`：最终结果未知；只允许查询或人工核验，不允许新建或重提。

只有明确成功或明确拒绝才清除待处理订单。重复点击、App 重启、超时、解析失败和网络结果未知都不能自动创建第二个订单。生产恢复记录以最小化的受保护磁盘日志保存：临时文件完整同步后原子替换，并同步从 Application Support 到支付目录的完整目录链；任一写入、同步或旧记录迁移失败都会闭锁建单。恢复记录只包含订单恢复必需的非密码状态，不包含原始六位密码、安全键盘材料、映射密码、Token、Cookie、Authorization 或完整请求体。

## 密码与传输边界

- 六位原始密码仅在用户点击确认后的短暂内存对象中存在；映射完成或任何退出路径都会立即覆写并清空，不写日志、不持久化、不进入剪贴板。
- 动态安全键盘材料按订单获取，不跨订单复用；浴室按 Android 当前生产协议使用对应的固定兼容材料。任何映射值都不得出现在日志、诊断页或文档中。
- 支付网络会话使用临时配置，不使用共享 URL cache、Cookie store 或 credential store；会话 Token/Cookie 仅在内存中传递。
- 请求策略严格限制 HTTPS 主机、端口、路径、方法、查询字段、表单字段和签名；自动重定向关闭，意外目标会失败关闭。
- 允许记录的诊断仅限功能类型、有限状态和脱敏错误；禁止记录姓名、学号、手机号、账户、余额、订单号明文、Token、Cookie、Authorization、密码、签名、键盘映射以及完整请求/响应体。

## 自动化与真机验收

GitHub Actions 和自动测试不得连接真实扣款接口，也不得执行自动扣款。CI 同时设置应用级禁写环境开关并在 runner 主机层阻断支付域名；URLProtocol/Mock 测试使用完全本地的合成响应验证字段、固定签名向量、Gson `third_party` 顺序/空值语义、OkHttp 表单特殊字符固定向量与独立服务端解码往返、键盘映射、成功、拒绝、超时、未知状态、恢复和重复点击。

代码与自动化通过后，PAY-01、PAY-02、PAY-03、PAY-05 的状态为“客户端已实现，待真机小额验收”，而不是“缺少安全 broker”。真机最终确认只能由获授权测试者手动执行，并按 `docs/migration/payment-device-acceptance.md` 核对订单和余额；自动化通过不能代替真实资金链路验收。
